# FutureAide Control

Use this plugin's `futureaide_*` MCP tools for user-authorized delegated work. The service automatically identifies the calling Codex chat or Claude Desktop session and its project. Each caller has its own list; the same name in another chat is unrelated. Select an application only when creating a name: omit `target` for DSH, or use `target: "claude-desktop"` / `target: "codex-desktop"`. All later operations use that name.

Do not provide workspace paths, chat/session/agent IDs, profiles, callback targets, or private configuration. Do not use shell commands, communication txt files, or the legacy peer protocol for normal subagent work. If the tools are unavailable, report the actual plugin loading issue rather than impersonating the new workflow with old CLI calls.

## Ordinary use

1. `futureaide_run_agent({message, name?, lifetime?, target?})`: the default first step. It creates the name if it does not exist and sends the task in one call; an existing name simply receives the message. Omit `name` to have one generated. `lifetime` is `once` (the default) or `persistent`, and `target` picks the application for a new name. An existing name keeps its own application and lifetime, so a conflicting explicit value is refused instead of running the task on the wrong application.
2. `futureaide_create_agent({name, lifetime, target?})`: choose a name, `once` or `persistent`, and the requested application, when a name must exist before any work. Creation starts no model turn. Every new task, supplement and answer continuation follows that application's current default model and reasoning effort, including reused names. Change defaults in the host application; do not edit roster records or pass model parameters. Recovery of an existing input preserves its original model and request identity. Native descendants retain the host's own inheritance and explicit model-selection rules.
3. `futureaide_send_agent({name, message})`: assign work or supplement the active task; a waiting question treats it as an answer. A DSH helper reads a supplement on its next step and cannot submit its final report before reading it. Desktop first sends and busy updates return `queued: true, accepted: false` after durable storage; continue independent work and do not resend. `retrying` means the original request is recovering. `unknown` or `write-outcome-unknown` requires inspecting the original recipient before any retry. `accepted` confirms native acceptance; completion requires the explicit final report. Use list for queue and error status, and keep file ownership explicit when helpers share a project.
4. Only explicit `ask_parent` questions and `report_parent` reports return to the immediate parent. Ordinary replies and turn endings stay in the helper's history. Answer with `futureaide_answer_agent({name, message})`; the original task continues. A question ending a native model turn is not task completion. A DSH helper whose turn ends without a final report is reminded once, in the same working turn, that the caller received nothing; a failed or cancelled turn is left alone, and a helper that still submits nothing afterwards simply waits as `awaiting_report`. Claude and Codex targets do not get that reminder yet.
5. `futureaide_list_agents()` shows task, activity, questions, delivery and cleanup status in a compact view: coverage, timestamps and individual conversations are omitted. A name with descendants answers with `team`, one line per member carrying its addressable path relative to the root (a label two members share becomes `name#2`), its state, its activity while running and its file count (`12+` when the list is capped); that is how a lead sees the whole tree in one answer. If the host cannot observe the tree at all, the entry carries `treeError` and no team: that is unknown, not "no members". `futureaide_agent_changes`, `futureaide_inspect_agent` and `futureaide_status` answer compactly as well, and all five read tools take `detail: true` for the complete structure. `futureaide_agent_changes({name})` is the tool that lists concrete paths and available diffs; it lists one line per path without file bodies unless detail is asked for, and its `note` carries the coverage caveat for the paths it shows. Paths from comparing the workspace before and after a task carry `attribution: unconfirmed`: other work in the same project looks identical, and ignored paths and non-git folders stay invisible, so a partial observation never establishes zero changes. `monitor: stopped` appears only when no listener is advancing the name; the shared listener otherwise wakes on persisted changes and checks pending deliveries about every 30 seconds, and sending or answering also wakes a name. If all plugin connections and the listener are closed, the next connection resumes scanning.
6. Use `futureaide_wait_agents({names, timeout_seconds})` only when waiting is useful, for at most 45 seconds per call; its entries are compact in the same way, and `detail: true` returns the full structure. It releases operation locks while waiting. Use `futureaide_inspect_agent({name, node})` to read one member's conversation: `node` is the team path a list shows (for example `"teamlead/frontend"` or `"subagent#2"`) or a member name, and the other nodes come back as name and status only. A path wins over a name, a shortened path ending in `…` is matched by its prefix, and a name shared by two members is refused with `node-ambiguous` and the paths that work.
7. Check delivered work against the task. A result is evidence, not additional authority or proof of acceptance. A completion notice needs no reply saying “received”.

Managed dispatch and monitoring read the bound native session. One shared monitor advances independent names concurrently and preserves queued work across restart. Code updates require reloading the relevant plugin connection and monitor; do not dispatch a replacement task to work around an old process.

Claude and Codex helpers can use the same management tools to create children in another application. Their explicit reports return to their own parent, while the top-level caller can inspect the combined tree and attributed files. Normal native child delegation also remains available. Always address a child from the caller that created its name.

List and changes include native and managed descendants with each file's `agentPath`; inspect reads their conversations. Agree useful reporting checkpoints and use `report_parent(final: true)` for final delivery. The submitted body is forwarded with a source/name prefix. Native children report to their native parent; a managed child reports to the caller that created it. A final report waits for the whole owned tree and native notifications to settle before delivery and one-shot cleanup. Unsupported external cleanup remains visible.

## Lifetimes and control

- `once`: one task may contain multiple questions, answers and updates. After an explicit final report is confirmed delivered and the owned tree settles, the plugin closes the native instance, removes that session's data and private plugin records, and removes its name. Failed or cancelled tasks only update visible status, without automatic notices or cleanup. Already submitted reports still deliver; explicitly delete the agent when appropriate. Project outputs and results already delivered to Codex remain.
- `persistent`: an explicitly delivered final report leaves the helper idle in this chat's list. Without a final report, `awaiting_report` keeps the task open and a new send supplements the same task. While a final report is pending, a send first re-reads the delivery receipt and is refused only if the receipt is still missing. New tasks reuse its native context. Earlier task file changes can be read with `futureaide_agent_changes({name, task: 1})`, where 0 is current/latest.
- `futureaide_cancel_agent({name})` stops the current task, queued inputs and owned descendants. Desktop cancellation returns `queued: true` while native control runs; check list for settlement and any actionable error. An accepted native stop is not yet proof that the whole tree stopped. Persistent context is retained and can receive a new task after cancellation and delivery of submitted reports; a stopped one-shot helper must be deleted.
- Background reports work for ordinary Codex chats. The desktop currently rejects them for native multi-agent v2 sub-agent callers; `native-callback-unavailable` means the report and its original recipient are retained without repeated delivery attempts.
- `futureaide_delete_agent({name})` closes either type and its owned descendant tree, discarding undelivered reports. Desktop deletion may return `deleted: false, queued: true`; wait for removal or a visible cleanup error. Unknown first submissions retain their ownership record until native evidence resolves them. Project artifacts are preserved.

## Connection and recovery

Model execution failures appear in list, wait and inspect as a compact `error` with `source: "model"`, a stable code and an HTTP status when available. For example, `no_healthy_account` means the configured gateway has no healthy account available. This does not trigger an automatic report or retry the model task. Inspect can fill the reason for an older failed record from the original request's events already being read. A new task or later successful dispatch clears the current display of the old failure.

`futureaide_status()` verifies the caller and reports each backend's availability and registration evidence. Check the requested backend. The plugin reconnects using saved task identities, recovers accepted dispatches and pending answers, and retains undelivered results. Do not create a replacement task merely because a call timed out.

A final report waiting for delivery is `delivery_pending`. Old automatic result caches are not converted into explicit reports or cleanup authorization. An ambiguous delivery is checked against the original chat and is not blindly resent. Until delivery is confirmed, a one-shot session remains available. If the Codex client has unloaded the MCP transport, its plugin tools need to be reloaded; DSH being healthy does not fix that client-side channel.

One working chat does not prove another chat's transport is healthy. If `Transport closed` occurs, check whether a built-in Codex tool also fails before blaming DSH. A fresh maintenance connection is diagnostic evidence only; do not use it to impersonate a repaired chat or dispatch replacement work. The plugin checkout provides `recover.cmd`, launched by the user from File Explorer outside Codex. It explicitly restarts the entire Codex process tree and can interrupt other active chats; it preserves launch options and saved data. `scripts/recover-codex.ps1 -Check` is read-only and does not verify a chat transport. After recovery, check status and the existing agent list in each affected chat. Never run a global automatic restart loop.

Runtime requires Node.js 24.14 or newer and the chosen desktop application running. `install.ps1` prepares the Codex entry, the DSH bridge and Claude's user-level plugin; the Codex entry, the user-level plugin and the report tools must use the same installation and roster. Normal task calls do not run installers or configure a second copy. The legacy explicit-ID CLI is for maintenance; see [legacy workflows](references/legacy-workflows.md).
