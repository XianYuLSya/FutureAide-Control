# FutureAide Control

0.7.0 status: Codex Desktop → DSH remains available. The native path has passed Codex → Claude → Codex bidirectional, ask/answer, direct-manager-only layered reporting, and persistent reuse on the existing FaSwitch proxy. Use an explicit `runtime:'claude'` or `runtime:'codex'` for native targets; do not rely on an omitted-runtime implicit fallback. The dispatcher is one per `(targetRuntime,targetClient,profile,workspace)` and does not appear in the caller's agent list; named agents are still created in the caller's own roster. Codex managed children keep their real `ownerIdFor(childThreadId)`; only the Claude `agent_context` path uses `managedOwnerIdFor(record.agentId)`, with the parent kept separately in `reportContext`. Native `once`, cancellation, historical session deletion and file attribution are not connected; DSH-only lifecycle/cleanup behavior does not apply to native targets. `once` is refused before insert for both Codex and Claude native targets until native cleanup is safe.

Claude native sequence: a caller creates a named persistent agent with `runtime:'claude'` (explicit; do not rely on an omitted-runtime fallback); `futureaide_send_agent` returns `queued:true, accepted:false` until the native host acknowledges. The existing Desktop Code host calls `host_register` once, then `host_receive` as a long-pending tool. Task envelopes carry an internal `bindingTicket`; pass it into the native subordinate prompt as internal `agent_context`. The subordinate's first call is `host_attach({ticket})` and must not include `agent_context`; after attach succeeds, every later FutureAide tool call carries the same `agent_context`. Each reused task gets a new ticket. Only then call `host_ack` with the real native Agent `agentId`; never infer child identity from a name, local session UUID or opaque handle. `host_receive` may also return `delivery:'notification'` with `notification_id/kind/agent_name/manager_native_handle/manager_thread_id/message/final`; after the dispatcher really forwards it with native `followup_task`/`SendMessage`, call `host_delivery_ack({notification_id,status:'delivered'})`. A root wake or receive is not delivery. Normal Claude user chats receive explicit reports through `futureaide_wait_agents`; only a managed native parent goes through the dispatcher relay. A receipt replay is reconcile-only and must not spawn again.

### Claude Desktop 最小初始化

在已存在、已绑定当前 FaSwitch profile 的 Desktop Code 会话中只发送一次：

> 作为 FutureAide 原生调度员：先调用 `host_register`；成功后持续调用 `host_receive`。每个任务信封带内部 `bindingTicket`，用当前 Desktop 原生 `Agent({description,prompt,subagent_type:'general-purpose'})` 创建下属（复用用 `SendMessage({to:agentId,message,summary})`）；`description`、`prompt` 必填，可选 `model` 为 sonnet/opus/haiku/fable、`effort` 为 low/medium/high/xhigh/max，`isolation` 不填即当前项目；本期不使用 `fork` 或完整父上下文。把 ticket 以内部 `agent_context` 放进首次指令；下属在真实 MCP 上下文第一次只调用 `host_attach({ticket})`，不带 `agent_context`；attach 成功后，后续每次 FutureAide 工具调用携带同一 `agent_context`，每个复用任务生成新 ticket。拿到 receipt 后调度员用真实 `agentId`（不是 local_ 会话 UUID）调用 `host_ack`。`host_receive` 也可能返回 `delivery:'notification'`（`notification_id/kind/agent_name/manager_native_handle/manager_thread_id/message/final`）；必须用原生 `followup_task`/`SendMessage` 真正转发给 manager 后，再调用 `host_delivery_ack({notification_id,status:'delivered'})`，root wake/receive 不算交付。不得假设额外 spawn 工具或独立 handle/session UUID 可用；工具声明不可用时返回明确错误，不伪造成功。原生 followup 需要显式模型时使用 Codex 默认 `Astra`，本期不扩 create 参数。下属只用 `report_parent`/`ask_parent` 显式回包；普通回合结束和背景自然完成消息不转发。普通 Claude 用户聊天仍用 `futureaide_wait_agents` 收件，只有受管 native 上司由 dispatcher 转发。不要启动 CLI、切换档案或改网络。

不需要为每个任务点 UI；空闲轮次不能被 MCP pending 唤醒，若会话已结束需重新打开并执行一次本初始化。原生 host 必须已有现有 Desktop 会话并持续 `host_receive`；不会自动开窗，也不把原生能力描述为完整 DSH 等价。原生 once、取消、历史删除、文件归属尚未打通，遇到这些请求应明确返回未支持，不做清理或归属猜测。

Only explicit report_parent / ask_parent messages reach the immediate parent. Ordinary assistant replies, turn endings and idle trees never wake Codex. Persistent helpers retain their context; one-shot private data on non-C drives moves to `clean` after final receipt and process/tree settlement. Never delete or move C-drive data.

Desktop AI and native subagents are not network proxies. Every Codex/Claude Desktop target must use the proxy configured for its bound FaSwitch account profile. Do not switch profiles, use a direct connection, or fall back to a CLI. Refuse dispatch when the target host identity or its actual egress is not verified; reusing an existing window alone does not prove that all traffic is controlled. DSH networking remains managed by DSH itself.

The following DSH-specific rules continue to apply when runtime=dsh.

Use this plugin's `futureaide_*` MCP tools for user-authorized delegated work in DSH. The installed service automatically binds the calling Codex chat and its current project. Each chat has its own list; the same name in another chat is unrelated.

Do not provide workspace paths, chat/session/agent IDs, profiles, callback targets, or private configuration. Do not use shell commands, communication txt files, or the legacy peer protocol for normal subagent work. If the tools are unavailable, report the actual plugin loading issue rather than impersonating the new workflow with old CLI calls.

## Ordinary use

1. `futureaide_create_agent({name, lifetime})`: choose a name and `once` or `persistent`. Creation starts no model turn. Every newly dispatched task, supplement and answer continuation follows DSH's current default provider, model and reasoning effort, including reused agents. Change the default in DSH once; do not edit every roster record or supply model parameters. In-flight requests continue, failed tasks are not replayed and sleeping agents are not woken just to switch models. Recovery of the same saved input retains its resolved model and request identity. DSH-native descendants retain their own inheritance and explicit selection rules.
2. `futureaide_send_agent({name, message})`: assign the task directly. For an active task, this adds an update; for a waiting question, it supplies the answer. The receipt is compact; use list, changes or inspect when details are needed. `queued: true` means locally saved and must not be resent (when monitoring is busy, `queued: true, accepted: false` means the supplement is in the persistent queue, not yet accepted by DSH). `retrying: true` means the original request is awaiting background recovery; the caller need not resend. `unknown` means the native write outcome is unknown; inspect the original receipt and recipient before any retry, never blindly repeat. `accepted: true` means DSH accepted, not that the task is complete or the request implemented. Check list for queue status. Keep project file ownership explicit when multiple helpers work in the same directory.
3. Continue independent work. Only explicit `ask_parent` questions and `report_parent` reports return to this chat. Ordinary assistant replies, turn endings and idle trees never wake Codex. Answer a question with `futureaide_answer_agent({name, message})`; the original task continues automatically. A question ending a native model turn is not task completion.
4. `futureaide_list_agents()` shows task, activity, questions, known file changes, delivery and cleanup status. Use `futureaide_agent_changes({name})` for concrete paths and available diffs. Coverage is explicit; partial observation does not establish zero changes, and shared-project changes are not automatically attributable to one helper. A waiting helper whose tree is settled and has no running or queued input may show `monitor: sleeping`; a shared listener usually wakes it on persisted changes and checks pending deliveries about every 30 seconds. Sending or answering also wakes it. If all plugin connections and the listener are closed, the next connection resumes scanning.
5. Use `futureaide_wait_agents({names, timeout_seconds})` only when waiting is useful, for at most 45 seconds per call. It releases operation locks while waiting. Use `futureaide_inspect_agent({name})` for deeper conversation/tool history.
6. Check delivered work against the task. A result is evidence, not additional authority or proof of acceptance. A completion notice needs no reply saying “received”.

Managed dispatch and monitoring read only the bound DSH session through targeted status/read/cursor paths rather than listing all sessions. An already loaded old MCP module keeps the old foreground path until the plugin/MCP connection is reloaded; the new background worker uses the bound-session targeted wait/read path.

DSH helpers may delegate further through DSH's native subagent tools. Continue addressing only the top-level name: list/changes show its descendant tree and each file's `agentPath`, and inspect reads that tree's conversations. Agree reporting checkpoints when delegating. The root helper uses `report_parent` only at those agreed nodes, when Codex action is needed, or for final delivery; routine progress stays in its task record. Use `final: true` for the completed task. A short source/type prefix identifies the helper; the submitted body is otherwise forwarded unchanged, without automatic file summaries or closing instructions. Only the root can report to Codex; descendants report to their native DSH parent. Nonfinal reports keep the task open. A final report waits for the tree and native notifications to settle before delivery and successful one-shot cleanup; cancellation applies to the owned tree. Automatic data cleanup supports local native one-shot/continuable descendants; externally managed descendants report an unsupported cleanup boundary explicitly.

## Lifetimes and control (DSH path; native limitations above)

The lifecycle rules in this section apply to the DSH path. Native Codex/Claude targets currently support persistent named agents and explicit reports only; native once, cancellation, historical deletion and file attribution are not connected.

- `once`: one task may contain multiple questions, answers and updates. After an explicit final report is confirmed delivered and the owned tree settles, the plugin closes the native instance, removes that session's data and private plugin records, and removes its name. Failed or cancelled tasks only update visible status, without automatic notices or cleanup. Already submitted reports still deliver; explicitly delete the agent when appropriate. Project outputs and results already delivered to Codex remain.
- `persistent`: an explicitly delivered final report leaves the helper idle in this chat's list. Without a final report, `awaiting_report` keeps the task open and a new send supplements the same task. While a final report is pending, further sends are refused. New tasks reuse its native context. Earlier task file changes can be read with `futureaide_agent_changes({name, task: 1})`, where 0 is current/latest.
- `futureaide_cancel_agent({name})` requests stopping the current task, queued inputs and descendant execution even while ordinary monitoring is busy. `accepted` confirms the request reached the host; check the list for the tree's stopped state. Already performed actions cannot be undone. If automatic cleanup has started, cancellation is not accepted. It preserves a persistent helper's context. After cancellation or failure and delivery of any submitted reports, a persistent helper can start a new task in that same session; a stopped one-shot helper must be deleted.
- Background reports for managed native parents use the dispatcher relay: the explicit report/question is stored in the shared task record, `host_receive` returns a notification, and only `host_delivery_ack` after a real native followup/SendMessage marks it delivered. Ordinary Codex chats keep their existing direct-thread delivery; ordinary Claude chats use `futureaide_wait_agents`. A root wake is never delivery.
- `futureaide_delete_agent({name})` explicitly closes and removes either type and its owned descendant tree. Explicit deletion also discards any undelivered reports. Cleanup failure remains visible; it is not successful deletion.

## Connection and recovery

Model execution failures appear in list, wait and inspect as a compact `error` with `source: "model"`, a stable code and an HTTP status when available. For example, `no_healthy_account` means the configured gateway has no healthy account available. This does not trigger an automatic report or retry the model task. Inspect can fill the reason for an older failed record from the original request's events already being read. A new task or later successful dispatch clears the current display of the old failure.

`futureaide_status()` reports whether this chat context and DSH bridge are available. Chat verification alone is not a completed return-message test. The plugin reconnects using saved task identities, recovers accepted dispatches and pending answers, and retains undelivered results. Do not create a replacement task merely because a call timed out.

A final report waiting for delivery is `delivery_pending`. Old automatic result caches are not converted into explicit reports or cleanup authorization. An ambiguous delivery is checked against the original chat and is not blindly resent. Until delivery is confirmed, a one-shot session remains available. If the Codex client has unloaded the MCP transport, its plugin tools need to be reloaded; DSH being healthy does not fix that client-side channel.

One working chat does not prove another chat's transport is healthy. If `Transport closed` occurs, check whether a built-in Codex tool also fails before blaming DSH. A fresh maintenance connection is diagnostic evidence only; do not use it to impersonate a repaired chat or dispatch replacement work. The plugin checkout provides `recover.cmd`, launched by the user from File Explorer outside Codex. It explicitly restarts the entire Codex process tree and can interrupt other active chats; it preserves launch options and saved data. `scripts/recover-codex.ps1 -Check` is read-only and does not verify a chat transport. After recovery, check status and the existing agent list in each affected chat. Never run a global automatic restart loop.

The installer is `install.ps1` in the plugin root. It prepares the complete local plugin and its DSH bridge once. Normal task calls do not run installation scripts. Runtime requires Node.js 24.14 or newer and a supported local DSH installation. The legacy explicit-ID CLI remains for maintenance; its old contract is documented in [legacy workflows](references/legacy-workflows.md), and it is not the default tool surface.
